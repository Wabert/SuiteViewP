# TN3270 terminals and decoder pipeline

## Switch A terminal

The Mainframe window's **Mainframe Terminal** tab shows a single **Switch A**
pane (`SwitchTerminalScreen`, holding one `MainframeTerminalScreen("A")`;
`terminal_for("A")` returns it). The earlier side-by-side Switch B pane was
removed (October 4, 2026); `switch_sessions` still stores a `switch_b`
endpoint, but nothing shows it.

- **Endpoints.** Each side's host/port/SSL/terminal type lives in
  `settings/terminal_settings.json` as `switch_a` / `switch_b`
  (`suiteview/mainframe_nav/switch_sessions.py`). A side never saved falls back
  to the pre-Switch flat keys, else `PRODESA:992` SSL. Change a side with that
  pane's **⚙️ Settings** (which also has the port scanner).
- **Sign-on.** User ID and password come only from the shared Passwords store
  (`suiteview/data/mainframe_credentials.py`, the encrypted `MAINFRAME_USER`
  row). Edit it with **🔑 Passwords** (Mainframe window footer or taskbar
  **Tools** menu; `suiteview/ui/dialogs/passwords_dialog.py`). The Password
  Manager is the role-granted app `PASSWORDMANAGER` — ADMIN only (via AllApps)
  for now; without it the entry points are hidden and `open_passwords_dialog`
  refuses with the role message. Mainframe Nav (FTP) reads the same sign-on. Older builds stored the password in plain text
  in `terminal_settings.json`; `retire_plaintext_credentials()` moves it into
  the store (never over an existing one) and removes it from the file.
- **Auto sign-on.** Region buttons and `open_policy(policy, company, region)`
  run `start_cics_sequence`; a missing sign-on opens Passwords instead of
  failing. Only CKAS, CKMO, CKPR and CKSR have navigation
  (`CICS_REGION_OPTIONS`); other regions are refused with a message.
- **PolView hand-off.** PolView's **🖥 Switch A** header button is shown only
  when the user's role is `ADMIN` and that role has `MAINFRAMENAV` (AllApps or
  explicit grant); other roles with `MAINFRAMENAV` do not see it. The click
  rechecks live access (`guard_switch_a_button`) and calls
  `MainframeWindow.open_policy_in_switch("A", policy, company, region)` through
  the taskbar's shared Mainframe window (`_launch_switch_with_policy`), or a
  PolView-owned window when run standalone.

### Screen-driven navigation to a policy on 62D2

`mainframe_navigator.cyberlife_navigator.CyberLifeNavigator` (wrapping
`switch_navigator.SwitchNavigator`) recognises each screen and returns one step
at a time; `MainframeTerminalScreen._navigate_to_transaction_screen` performs
the step, waits for the host's reply to settle, and asks again. These modules
live in the shared, standard-library-only `Dev\Mainframe_Navigator` package
(also the home of Albert's mainframe tools), installed into SuiteView's venv in
editable compat mode by `requirements.txt` and bundled through `SuiteView.spec`.
Change and test screen knowledge there, not in SuiteView. The verified
CyberLife production path (Switch October 1, CICS October 4, 2026):

| Screen | Recognised by | Step |
| --- | --- | --- |
| Logon | `USER ID` + `PASSWORD` + `===>` | user ID and password into the first two input fields, Enter |
| Message (e.g. password-expiry notice) | `Press "CLEAR" or "PF3" to continue` | PF3 |
| VTAM/Switch main menu, Level 1 | `Session Selection` + `Level:1` | option named `CICS` (3) |
| CICS REGIONS, Level 2 | `Level:2` | option named `CICSCYB` (4) |
| CICS CYBERLIFE REGIONS, Level 3 | `Level:3` | option named for the APPLID, e.g. `CICSCKPR` (7) |
| Continue | `*** PRESS ENTER TO CONTINUE ***` | Enter |
| CICS welcome | `Welcome ... CICS/TS` | `0000` replaces `MENU` in the first field, Enter |
| Terminal configuration | `SELECT TERMINAL CONFIGURATION` | PF labelled `TERMINALS WITH 24 PF KEYS` (PF2) |
| CyberLife system | `SELECT REQUIRED FUNCTION` | PF labelled `CYBERLIFE INFORCE SUBSYSTEM` (PF2) |
| Inforce function keys | `CURRENT FUNCTION KEY DEFINITIONS` | PF labelled `62D2,*.` (PF2) |
| Transaction screen (ready) | region banner, e.g. `CKPR-ANICO`, on the last row | `62D2,<policy padded to 10>;newco=<company>;.`, Enter |

- Options and PF keys are chosen by **label**, so renumbered menus still work.
  A Level 2+ Switch menu without the path (for example IMS REGIONS) backs out
  with PF7.
- The pane's policy lookup succeeds only when the reply says `DISPLAY COMPLETE`
  and its command line echoes the same policy; otherwise the host's message
  (e.g. `16 RECORD DOES NOT EXIST`) is shown. The company is always sent (blank
  means 01). A command is never typed if it does not fit the input field.
- An already-connected pane continues from its current screen: any Switch
  screen, or a CyberLife screen of the region this pane navigated into (a
  transaction screen's banner must match). So a second policy on the same
  region is a single 62D2 command. Other screens start a fresh connection.
- The navigator **stops** rather than guessing: a host message after a menu
  selection (e.g. `(GSLSSOPC) ** APPL CICSCKPR ... UNAVAILABLE` when the region
  is down) is shown in the pane's status; a logon screen returning after
  sign-on stops without re-sending the password (lockout protection); an
  unrecognised screen, a screen an action did not advance, a missing PF label,
  a banner for another region, or no reply within `SWITCH_REPLY_TIMEOUT_MS`
  also stop.
- **Session in use elsewhere** (verified October 4, 2026): if the user ID is
  already signed on at another terminal, Enter on the logon panel returns it
  with `(GSPPRLHE) USER ON TERM <terminal>-TO ACQUIRE,ENTER PASSWORD AND PRESS
  PF1`. The pane asks before taking that session over (it disconnects the
  other terminal); on Yes it re-enters the user ID and password and sends them
  **with** PF1, once. No leaves the other session alone and stops.
- Automation never logs a password: hidden fields, and any field containing
  the saved password, are logged only as `<hidden, n chars>`.
- MULTIPLE LOGON (PF6 once) and the `OPEN <applid>` secondary session are kept
  from the proof of concept and are not yet re-verified live.
- From a policy display, typing a record number (`6201`, `6202`, ...) over the
  transaction code shows that policy-record segment and PF2 returns to 62D2
  (walk-through; not automated yet). Only `62xx` display transactions are built
  by the shared package; `U1xx` quote/maintenance transactions can change
  policies and need their own reviewed, confirmed workflow.
- The port-1992 endpoint keeps its separate fixed sequence.

Recognition and decisions are tested in Mainframe_Navigator
(`tests/test_switch_navigator.py`, `tests/test_cyberlife_navigator.py`); the
pane loop in `tests/test_switch_auto_navigation.py`, all with screens from the
walk-throughs and placeholder policies.

## Decoder pipeline
`suiteview/mainframe_nav/tn3270.py` keeps socket I/O separate from protocol
decoding and screen mutation:

1. **`TelnetFrameDecoder`** consumes telnet IAC framing. It emits negotiation
   frames (`DO`, `WILL`, subnegotiation payloads) and complete 3270 records when
   `IAC EOR` is seen. Escaped `IAC IAC` bytes are preserved in the 3270 payload.
2. **`TN3270CommandDecoder`** classifies each record as a 3270 command and
   extracts the WCC/write payload where applicable.
3. **`ScreenApplier`** parses write data into `WriteOrder` dataclasses and
   mutates `Screen` through a handler table keyed by order byte.
4. **`TN3270Client`** owns sockets, replies to negotiation, dispatches decoded
   records, and sends outbound AID/read-modified byte streams.

## Telnet negotiation supported

- `DO TERMINAL-TYPE` → `WILL TERMINAL-TYPE`
- `SB TERMINAL-TYPE SEND` → terminal type `IBM-3278-2-E`
- `DO/WILL BINARY`
- `DO/WILL EOR`
- Basic `TN3270E` device-type and functions negotiation used by the existing
  client

## 3270 commands supported

Both standard and SNA/alternate command bytes are recognized where the previous
parser did:

| Command | Bytes | Behavior |
| --- | --- | --- |
| Write (W) | `0x01`, `0xF1` | Applies write orders without clearing |
| Erase/Write (EW) | `0x05`, `0xF5` | Clears the 24×80 screen, then applies write orders |
| Erase/Write Alternate (EWA) | `0x0D`, `0x7E` | Clears the screen, then applies write orders |
| Read Buffer (RB) | `0x02`, `0xF2` | No screen mutation |
| Read Modified (RM) | `0x06`, `0xF6` | No screen mutation |
| Write Structured Field (WSF) | `0x11`, `0xF3` | Handles Read Partition Query/Query List and sends a basic Query Reply |

## Write orders supported

| Order | Behavior |
| --- | --- |
| `SBA` | Sets the current buffer address |
| `SF` | Starts a field, stores the basic attribute, and records field metadata |
| `SFE` | Starts a field using the basic 3270 field-attribute pair (`0xC0`) when present |
| `SA` | Parsed and skipped |
| `MF` | Parsed and skipped |
| `IC` | Sets the screen cursor to the current address |
| `PT` | Parsed and skipped |
| `RA` | Repeats one EBCDIC character up to the target address |
| `EUA` | Writes blanks up to the target address |
| `GE` | Writes the escaped graphic character as the current EBCDIC translation |

Regular bytes are translated with the module EBCDIC table and written at the
current address. The parser still preserves the historical final-cursor rule:
after a write, the screen cursor is the final current address even if `IC`
appeared earlier in the stream.

## Known gaps

- No TN3270E response-request handling beyond the existing basic negotiation.
- `SA` extended attributes and `MF` modifications are recognized but not applied
  to the display model.
- `PT` does not search for the next unprotected field.
- Character-set coverage is limited to the module's EBCDIC table; unknown bytes
  translate to spaces.
- WSF support is limited to Read Partition Query/Query List replies.

Golden byte-stream coverage lives in `tests/test_tn3270_golden.py`.
